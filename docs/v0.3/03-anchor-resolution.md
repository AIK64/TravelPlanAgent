# 地点锚点解析

LLM 只保留用户提供的抵达、离开和住宿地点名称，不生成坐标。`resolve_anchors` 将名称转成 `POISearchQuery(exact_match=True)`，经现有 Tool Gateway 获得标准化 `POIFacts`。

## 去重与匹配

- 按抵达、离开、住宿顺序建立检索计划。
- 相同规范化名称只调用一次工具；例如抵达和离开都是“杭州东站”，一个结果可回写两个 role。
- 优先要求规范化名称完全相等；没有完全匹配时才接受包含关系。
- 仅有一个候选才生成 `AnchorResolution`，其中包含 POI ID、坐标、provider 与 confidence。
- 零个候选产生 `not_found`；多个候选产生 `ambiguous`，二者都转为稳定澄清问题。

## 为什么不由 LLM 选择坐标

坐标属于可验证事实，应该来自地图工具。把它交给模型会产生不可追溯的幻觉，并让路线、缓存键和后续验证失去来源信息。当前规则刻意保守：无法唯一识别时宁可暂停，也不自动选“看起来最像”的 POI。

## 故障边界

`ToolResult.failed` 在进入匹配逻辑前转换为 `ToolUnavailableError`。成功的空结果是业务层“未找到”，失败结果是基础设施不可用；两者不能合并。轨迹测试覆盖了唯一匹配、空结果澄清、歧义和工具超时分支。

当前 Mock 数据只提供演示所需的杭州东站、西湖东侧与景点事实；它不是完整地图数据库。真实地点覆盖必须显式启用 AMap，并继续遵守相同的 Gateway 和失败语义。
